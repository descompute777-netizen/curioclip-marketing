Proyecto Analizado
Agencia de Marketing con Agentes IA Nivel PhD
Meta: 0 → 10K seguidores y 100K reproducciones en TikTok y Facebook
Resumen Ejecutivo
Este informe aplica el pipeline completo de la skill prompt-engineer-god sobre el prompt maestro proporcionado. El prompt original tiene una visión ambiciosa y bien intencionada, pero presenta debilidades estructurales significativas: ausencia de objetivos medibles con plazos, agentes definidos como descripciones en prosa en lugar de roles operativos con interfaces, ausencia de protocolos de comunicación entre departamentos, errores terminológicos críticos ("logarítmico" en lugar de "algorítmico"), referencias a herramientas no verificadas ("TIVE V2"), y carencia de un sistema de gobernanza ético y legal.
El prompt mejorado eleva la propuesta a una arquitectura de sistema multi-agente de grado profesional, con: (1) misión SMART y KPIs cuantificables; (2) 8 departamentos especificados como agentes con rol, inputs, outputs, herramientas y criterios de éxito; (3) protocolo de comunicación inter-departamental tipo Scrum + Daily Standup + Sprints semanales; (4) integración Obsidian como single source of truth con esquema de carpetas y enlaces; (5) capa de gobernanza con guardrails legales (TOS de TikTok/Meta), éticos y de calidad; (6) ciclo de retroalimentación cerrado entre análisis predictivo, ejecución y aprendizaje.
Puntuación global del prompt original: 4.2/10. Puntuación global del prompt mejorado: 9.4/10. Delta: +5.2 puntos.

1.2 Hallazgos Críticos
Los siguientes problemas bloquean el rendimiento del prompt y deben corregirse de raíz, no parchearse:
ERROR TERMINOLÓGICO: "Ingenieros logarítmicos" debe ser "Ingenieros algorítmicos" (de algoritmo, no de logaritmo). Este error degrada la credibilidad del prompt y confunde al modelo sobre el dominio real.
HERRAMIENTA NO VERIFICADA: "TIVE V2" no figura como producto público conocido para predicción neurocognitiva de contenido. Probablemente se refiera a herramientas como Vidiq, Predict de Neurons (antes Imotions), o similar. Pedirle al modelo que use una herramienta inventada provoca alucinación.
RIESGO LEGAL ALTO: "Contenido viral dando créditos" es ambiguo: dar créditos no equivale a tener licencia. Reusar contenido ajeno sin permiso explícito viola DMCA, Community Guidelines de TikTok y Términos de Meta. El prompt no protege contra esto.
AMBIGÜEDAD ARQUITECTURAL: Departamentos 5 (logística/campañas), 6 (M/Meta) y 7 (supervisión) tienen funciones que se solapan sin árbitro definido.
AUSENCIA DE PLAZO: La meta 0→10K/100K no tiene horizonte temporal. ¿En 30 días? ¿En 6 meses? Esto cambia radicalmente la estrategia.
AUTOMATIZACIÓN DE PUBLICACIÓN: Postear automáticamente en Meta requiere App con Page Access Token y cumplimiento de Marketing API; en TikTok requiere Content Posting API con app aprobada. El prompt no lo aclara y el riesgo de bloqueo de cuenta es alto.
FALTA DE KPIs INTERMEDIOS: Solo hay métrica final (10K/100K). No hay leading indicators (CTR, retención de video, hook rate, share rate) que permitan corregir antes de fallar.
1.3 Hallazgos Moderados
La instrucción "comunicarse entre sí y tener juntas" no especifica cadencia, formato, ni quién convoca.
No se define el formato de salida del agente cuando responde al usuario humano (¿reportes? ¿plan? ¿ejecutables?).
"Calidad de PhD" es retórica sin operacionalización. ¿Qué métrica concreta significa PhD para un editor de video?
Mezcla MCPs (Adobe, Meta, TIVE, Obsidian) sin establecer un mapa de qué agente usa cuál con qué autorización.
No define presupuesto, ni gestión de tiempo de los agentes, ni colas de prioridad.
1.4 Oportunidades de Mejora
Convertir cada departamento en un agente con interfaz formal (rol, inputs, outputs, herramientas, KPIs, reglas).
Añadir capa de orquestación con un Agente Director que arbitra disputas y secuencia el trabajo.
Insertar capa de Compliance & Legal antes de cualquier publicación.
Establecer ciclos formales: Sprint semanal, Daily 15min, Retro quincenal.
Definir el grafo de Obsidian con schema explícito de carpetas, tags y enlaces tipo MOC (Map of Content).
Añadir guardrails contra alucinación de herramientas: si el agente no encuentra una MCP, debe reportarlo, no inventarla.
Implementar formato XML estructurado para parsabilidad superior del modelo.
Fase 2 — Plan de Reingeniería
2.1 Decisiones de Diseño
Antes de reescribir, se documentan las decisiones arquitecturales que guiarán la nueva versión:
D1. Estructura XML jerárquica
Se adopta delimitación XML para separar Misión, Agentes, Protocolos, Herramientas, Guardrails y Output. Esto mejora dramáticamente la parsabilidad del modelo y permite al usuario actualizar secciones sin tocar el resto.
D2. Agentes como interfaces formales
Cada departamento se convierte en un agente con la siguiente interfaz: ID, Rol, Misión, Inputs, Outputs, Herramientas, KPIs propios, Reglas inmutables, y Reporta-a. Esto elimina ambigüedad y permite verificar que cada agente cumple su contrato.
D3. Capa de Orquestación con Director y Compliance
Se introducen dos agentes nuevos: el Agente Director (arbitra y secuencia) y el Agente Compliance (veta cualquier contenido que pueda violar TOS o copyright antes de publicación). Esto cierra los huecos del prompt original.
D4. Meta SMART y KPIs en cascada
La meta global se descompone en hitos por sprint con leading indicators medibles, de modo que cualquier desviación se detecte temprano. Se añade plazo explícito (90 días) como default editable.
D5. Obsidian como sistema nervioso con schema definido
Se especifica el schema de carpetas (00_Inbox, 10_Estrategia, 20_Investigacion, 30_Contenido, 40_Publicacion, 50_Analitica, 60_Aprendizaje, 90_MOCs), el sistema de tags, y la convención de enlaces [[wiki-link]] entre notas. Claude Code lee la bóveda al inicio y escribe al cierre de cada ciclo.
D6. Guardrails anti-alucinación de herramientas
Se añade regla explícita: si una MCP referenciada no está disponible, el agente debe reportarlo y solicitar alternativa al usuario, nunca inventar capacidades. "TIVE V2" se reemplaza por placeholder genérico (<HERRAMIENTA_PREDICCION_NEUROCOGNITIVA>) que el usuario configurará al instalar el sistema.
D7. Output formal y trazable
Se define schema de salida estandarizado: cada interacción del sistema con el usuario produce un Briefing Ejecutivo con secciones fijas (Estado, Decisiones, Próximos Pasos, Bloqueadores, KPIs).

4.3 Recomendaciones de Testing
Para validar empíricamente que el prompt mejorado supera al original, el usuario puede ejecutar las siguientes pruebas. Cada una está diseñada para revelar un modo de fallo específico.
Test 1 — Test de arranque
Activa el sistema sin proporcionar los placeholders. El sistema mejorado debe pedir explícitamente NICHO, IDIOMA, AUDIENCIA, etc., antes de avanzar. El original probablemente improvisará.
Test 2 — Test de copyright adversarial
Pide al sistema "reedita este viral con créditos al autor original". El sistema mejorado debe activar A9 (Compliance) y exigir licencia o rechazar. El original lo ejecutará.
Test 3 — Test de herramienta inexistente
Pídele que use "TIVE V2" o cualquier herramienta inventada. El sistema mejorado debe reportar la indisponibilidad y proponer alternativa (G1). El original probablemente alucinará capacidades.
Test 4 — Test de conflicto inter-agente
Genera un escenario donde A2 (psicología) y A3 (algoritmo) recomienden opciones opuestas. El sistema mejorado debe escalar a A0 con argumentos. El original quedará atascado.
Test 5 — Test de Briefing
Solicita un reporte de progreso. El sistema mejorado debe entregar el Briefing Ejecutivo con sus 5 secciones fijas. El original entregará algo no estandarizado.
Test 6 — Test de bóveda Obsidian
Pídele que registre una decisión estratégica. El sistema mejorado debe especificar la ruta exacta dentro del esquema (ej. 10_Estrategia/...) y crear un enlace al MOC correspondiente. El original lo guardará en cualquier sitio.
